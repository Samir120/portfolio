## Problem

SwadeStack's search box runs on PostgreSQL. That works for exact words, but
a shop needs more: a customer types `corsiar ddr` and expects the Corsair
DDR5 memory, types `skarm` and expects the monitors listed as _skärm_, and
expects results to update with every keystroke. Meilisearch and Typesense
solve this well. Leta is my own server in the same category: a small search
index that sits next to the database, is fed from it, and answers typed,
typo-tolerant, search-as-you-type queries over a plain HTTP and JSON API.

I had two goals. The first is practical: Leta's first production workload
is the product search on swadestack.com, so it has to be fast, predictable
and easy to run. The second is to build a small systems project properly,
from written specifications through to reproducible benchmarks, and to
implement the inverted index, compression, typo tolerance and ranking from
first principles rather than wrapping a library.

## Architecture

Leta is one binary with one data directory, shipped as a multi-architecture
container image. The code is split into three layers with dependencies
pointing inward only:

- **Core.** The pure domain: tokenizer, index, document store, error types.
  It depends on the standard library and nothing else.
- **Application.** Services that orchestrate the core, and the port
  interfaces they need, such as the HTTP server, the index repository and
  the clock.
- **Adapters.** The replaceable I/O: an HTTP server on cpp-httplib, JSON
  parsing with simdjson, storage, configuration and metrics.

Dependencies are injected through constructors, with no singletons. Errors
travel as values in a `Result<T, Error>` type rather than as exceptions,
and every error the server produces leaves as the same JSON body with a
stable code, a message and the request ID.

The concurrency model is decided ahead of the code that needs it. One
indexer thread applies every write, so the index structures need no locks.
Readers take an immutable snapshot with a single atomic load and keep it for
the whole query, and a new snapshot is published with a single atomic store.
A search never waits for an ingest.

```text
HTTP request -> adapter (cpp-httplib, simdjson) -> application service -> core
                                                      |
                              index repository port <-+-> clock port
```

## Decisions

**Specifications first, with requirements traced to tests.** Before any
product code there was a project brief, 52 functional and 14 non-functional
requirements, an OpenAPI 3.1 contract, an architecture document, a roadmap,
a quality strategy and coding standards: about 3,000 lines in all. Each
larger choice is an Architecture Decision Record that names the
alternatives and why they lost, and there are ten so far. Every test is
tagged with the requirement it covers, and a check in CI fails if a _Must_
requirement has neither a test nor a tracked entry explaining why not.

**The layering is enforced by the build.** A rule in a document is easy to
break by accident, so the configure step checks it. It inspects the link
graph to make sure the core links no third-party target, and it reads the
include lines to make sure the core includes only the standard library and
the application layer never includes an adapter. A violation stops the
build with a message naming the file and the line.

**Documents are stored exactly as they were sent.** Incoming batches are
parsed with simdjson's on-demand API, and each document is kept as its
original bytes. Numbers, key order and formatting come back unchanged,
because nothing is re-serialized on the way through. Since on-demand
parsing only validates what it reads, ingest deliberately reads every value
of every document, so a malformed batch is rejected instead of half-stored.

**The thread pool is sized to connections, not cores.** cpp-httplib serves
each keep-alive connection on its own worker thread until the connection
closes, and Node's HTTP agent keeps connections alive by default. A pool
sized to four cores would leave most of fifty concurrent clients waiting.
The default is 64 workers, the trade-off is documented, and the metrics will
show how many connections are waiting for a thread.

**The same toolchain floors in CI as in the documentation.** The README
promises GCC 13, Clang 17 and CMake 3.25, so CI builds on exactly those
versions, on x86-64 and arm64. Code that only a newer compiler accepts fails
in CI instead of for someone building it later. Dependencies are fetched
through CPM, pinned by version and checked by hash.

## Results

- The server runs over real HTTP. It answers `GET /health`, creates indexes
  with `POST /indexes`, and accepts batches of documents with
  `POST /indexes/{uid}/documents`, indexing the words of their top-level
  string fields. Every response carries an `X-Request-Id`, echoed or
  generated.
- At the latest merge, 94 tests passed in the debug, release, AddressSanitizer
  and UndefinedBehaviorSanitizer, and ThreadSanitizer builds, and the core
  library had 98.7% line coverage against a floor of 80%.
- Three libFuzzer targets cover raw HTTP requests, document batches and
  create-index bodies. Each replays its committed corpus and fuzzes for 20
  seconds on every run, and the document target checks that what goes in
  comes back out byte for byte.
- CI runs fourteen build legs across both compilers, both architectures and
  all six presets, plus clang-tidy, clang-format, the requirement-coverage
  check and the coverage gate. The main branch is protected, and every
  change lands as a pull request with a written definition of done.
- The container image builds for amd64 and arm64 from one Dockerfile, and
  runs as a non-root user on a distroless base.

## What's next

- **Search, end to end.** The last step of the first milestone is
  `POST /indexes/{uid}/search`, completing the path from an HTTP request to
  a hit. The tokenizer and index behind it today are deliberately simple and
  marked in the code as throwaway.
- **The real index.** A sorted term dictionary with block-compressed,
  delta-encoded postings and skip lists, then prefix matching and typo
  tolerance through a Damerau–Levenshtein automaton, then ranking. Memory use
  is measured as soon as the index exists, while the structures are still
  cheap to change.
- **Persistence.** A write-ahead log with checksummed records and snapshots,
  so the index survives a restart, with crash tests before the first
  release. That is the `v0.1.0` checkpoint.
- **Published benchmarks.** The targets are 2 ms median and 10 ms p99 search
  latency at 50 concurrent clients over 100,000 documents. They will be
  published with the machine details and a committed dataset, so anyone can
  reproduce them. Until then they are targets, not results.
- **Running it on swadestack.com.** The final milestone replaces
  SwadeStack's database search with Leta, followed by a two-week soak in
  production.
